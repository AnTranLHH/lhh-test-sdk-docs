    Test Controller and settings

    Android only for running tests today.

    Open Settings

    LHH Test SDK → Settings

    Values are stored in EditorPrefs on your machine (not in git). Each QA machine keeps its own gRPC address, app path, and bundle id.

    Configuration (always visible)

    Field Purpose
    gRPC server address Test Controller URL. Default: http://127.0.0.1:5050.
    Bundle ID Optional override. If empty, the effective id is Player Settings → Application identifier. Must match the installed APK.
    Platform Use Android for now.
    App path Path to the automation-enabled .apk. Use Browse to pick the file dev or CI gave you.

    If App path is empty, setup may warn and the session cannot launch your build.

    Install and run the Test Controller (recommended)

    Use the Settings window instead of manual shell scripts.

    1. Enable Show Advance Settings.
    2. Install Test Controller — clones and prepares ~/lhh-auto-test-controller (runs environment check/setup as needed). Wait until the button shows Test Controller Installed.
    3. Run Test Server — starts Appium and the controller (default gRPC 5050, Appium 4723). Status should show Running before you run NUnit tests.
    4. When finished for the day, Stop Test Server.

    If install fails, read the Progress panel in Advance Settings. Missing JDK, Android SDK, or Appium usually requires a one-time machine setup—coordinate with dev/infra; QA’s normal path is still the Install Test Controller button.

    The running controller version should match the com.lhh.testcontroller.shared package version in your Unity project (see Install the Test SDK).

    What happens when a test starts

    The first LHH_TestSDK call in a Test Runner run (for example WaitForObject) automatically:

    1. Connects to the gRPC address in Settings.
    2. Requests a test device from the controller.
    3. Creates an Appium session and launches the App path APK when configured.
    4. Waits until the Unity player’s command hub is connected.

    You do not call setup APIs yourself in normal tests.

    When the Test Runner finishes the whole run (or reports a runner error), the SDK returns the device to the controller.
